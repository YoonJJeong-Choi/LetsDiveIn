# EC2 침해 사고 대응 기록

> 2026년 6월, 개인 포트폴리오 서버가 자동화 웜에 감염된 사고의 조사 및 복구 기록

## 요약

2026년 6월 28일, AWS EC2에 배포한 포트폴리오 서비스가 Next.js RCE 취약점을 노리는 자동화 웜에 감염되었다. 공격자는 약 1분 만에 크립토마이너(XMRig)와 Elasticsearch 랜섬웨어 스캐너를 설치했고, 서버는 이후 10일간 외부 스캔 노드로 사용되었다.

스캐너가 생성한 로그 파일이 4.48GB까지 증가해 디스크를 가득 채우면서 시스템이 재부팅되었고, 웜이 부팅 지속성을 설정하지 않은 탓에 그대로 활동을 멈췄다. 예산 임계치 알람으로 비정상 요금을 인지해 사고를 발견했다.

실제 피해는 데이터 전송 요금 약 2만 원에 그쳤으나, **탐지까지 10일이 걸린 점**이 이번 사고의 핵심 문제였다.

| 구분 | 내용 |

프론트엔드와 백엔드를 한 인스턴스에 배치해 애플리케이션 간 통신은 루프백으로만 이루어졌다.

## 초동 조치

조사에 앞서 다음 순서로 서버를 격리했다.

1. **보안 그룹 아웃바운드 규칙 전체 삭제** — 채굴 풀 연결 및 추가 페이로드 다운로드 차단
2. **인바운드는 SSH(22) / 관리자 IP만 허용** — 외부 웹 접근 차단
3. **EBS 스냅샷 생성** — 재구축 전 증거 보존

보안 그룹은 상태 저장(stateful) 방식이므로 아웃바운드 규칙을 모두 제거해도 SSH 응답 트래픽은 정상 반환된다. 이 상태에서는 악성 프로세스가 재실행되더라도 외부와 통신할 수 없어 안전하게 조사할 수 있다.

## 조사 과정

### 1. 악성 파일 탐색

```bash
sudo find / -xdev -iname '*xmrig*' 2>/dev/null
```

- 애플리케이션 디렉터리 하위 업로드 경로에서 발견
- `/tmp`나 `/dev/shm`이 아닌 **앱 디렉터리**라는 점이 첫 단서였다

### 2. 침해 시각(T0) 특정

```bash
stat xmrig.tar.gz
```

```
Modify: 2023-11-23 14:15:40
Change: 2026-07-02 09:03:13
 Birth: 2026-06-28 08:58:22
```

- `Birth` = 파일 생성 시각이므로 **T0는 2026-06-28 08:58:22**
- `Modify`가 2023년인 것은 XMRig 배포판의 원본 타임스탬프를 tar가 보존한 결과이며, 타임스탬프 위조가 아니다

### 3. 침해 파일 목록화

```bash
ls -la --time-style=full-iso [업로드 경로]/
```

- `scanner_linux` (9MB, 실행 권한 있음)
- `data.log` (4.48GB)
- `exploited.log`, `failed.log`, `scanner_deployed.log` (각 0바이트)
- 디렉터리 권한 **777** 확인

### 4. 디스크 점유 원인

```bash
df -h
sudo du -sh /home/ec2-user/* /var/log/* 2>/dev/null | sort -h | tail -15
```

- `/` 8GB 중 100% 사용, 여유 120K
- 애플리케이션 디렉터리 5.1GB — 대부분이 `data.log`

### 5. 악성 바이너리 분석

**웜의 정체와 공격 방식을 확정한 단계다.**

```bash
strings scanner_linux | grep -iE 'CVE-|elastic|exploit|payload' | sort -u
```

핵심 발췌:

```
[Next.js Scanner + Exploitation Framework]
Z:/Ransom_Botnet/Elasticsearch/go/worm.go
Next.js scanner with RCE detection + unauthenticated Elasticsearch ransomer
```

```javascript
var res = process.mainModule.require('child_process').execSync('%s', ...);
throw Object.assign(new Error('NEXT_REDIRECT'), {digest:`${res}`});
```

```bash
nohup ./scanner_linux -t 1000 >/dev/null 2>&1 &
```

- 명령 실행 결과를 리다이렉트 예외의 `digest` 필드에 담아 응답으로 유출하는 구조
- 배포 명령이 `nohup ... &` 형태 — **부팅 지속성이 없다**는 사실을 여기서 예측할 수 있었다
- 목적은 채굴이 아니라 **인증 없는 Elasticsearch를 찾아 데이터를 삭제하고 몸값을 요구하는 것**

### 6. 악성 활동 로그 확인

```bash
head -c 2000 data.log
head -50 monitor.log
```

```
2026/06/29 06:36:26 CLOSED: 117.102.19.1
2026/06/29 06:36:26 OPEN_80: 61.220.176.232
2026/06/29 06:36:26 OPEN_9200_ES: 95.86.101.79
```

- 전 세계 IP를 대상으로 80 / 443 / **9200(Elasticsearch)** 포트를 스캔한 기록
- 6/29 06:36 시작, 7/8 02:06까지 지속
- `exploited.log`가 0바이트이므로 **실제 공격 단계에는 도달하지 못했다**

### 7. 채굴기 설정 확인

```bash
cat xmrig-6.21.0/config.json
```

```json
"url": "donate.v2.xmrig.com:3333",
"user": "YOUR_WALLET_ADDRESS"
```

- 지갑 주소가 배포판 기본값 그대로 — **채굴은 실제로 이루어지지 않았다**

### 8. 공격 표면 확인

```bash
sudo ss -tulpn
ps aux | grep -iE 'node|next|java'
sudo nginx -T | grep -E 'access_log|proxy_pass'
```

- nginx(80/443) → Next.js v15.1.6(3000) + Spring Boot(8080) 프록시 구조 확인
- 외부 노출 포트는 80, 443, 22뿐이었고 Docker API·Redis 등 흔한 취약 포트는 없었다

### 9. 침입 경로 확정

**로그 원본으로 침입 요청을 특정한 결정적 단계다.**

```bash
sudo zcat /var/log/nginx/access.log-20260629.gz | grep "28/Jun/2026:08:5"
```

```
188.213.212.204 [28/Jun/2026:08:58:17] "GET / HTTP/1.1" 404 "Go-http-client/1.1"
188.213.212.204 [28/Jun/2026:08:58:18] "GET / HTTP/1.1" 200 "Go-http-client/1.1"
188.213.212.204 [28/Jun/2026:08:58:19] "POST / HTTP/1.1" 500 "Go-http-client/1.1"
...
188.213.212.204 [28/Jun/2026:08:59:14] "POST / HTTP/1.1" 499 "Go-http-client/1.1"
```

- User-Agent가 `Go-http-client/1.1` — 바이너리가 Go로 작성된 것과 일치
- `GET /` 200 응답으로 Next.js를 식별한 뒤 `POST /`를 12회 반복
- **500 응답은 실패가 아니라 성공 신호다.** 페이로드가 명령 실행 후 의도적으로 예외를 던지는 구조이기 때문이며, 응답 크기가 매번 다른 것(107~361바이트)은 실행한 명령마다 출력 길이가 달랐음을 뜻한다

### 10. 재접속 여부

```bash
sudo zcat access.log-20260629.gz | grep "188.213.212.204" | wc -l   # 14
sudo zcat access.log-2026070*.gz | grep "188.213.212.204"           # 결과 없음
```

- 공격자 IP의 요청은 침입 당시 14건이 전부
- 서버 운영 기간(~7/4) 동안 재접속 없음. 이후는 로그 부재로 확인 불가

### 11. SSH 침입 여부

```bash
last -20
cat ~/.ssh/authorized_keys
```

- 로그인 기록 전부 본인 접속 (`13.209.1.x`는 EC2 Instance Connect 서비스 대역)
- 등록된 공개키 1개, 본인 키페어

### 12. 지속성 조사

```bash
sudo crontab -l; crontab -l
sudo systemctl list-timers --all --no-pager
ls -la /etc/systemd/system/
cat /etc/ld.so.preload
```

- cron 항목 없음
- systemd 타이머 전부 OS 기본 항목
- 서비스 파일 2개 모두 T0 이전(6/27) 생성 — 본인이 등록한 애플리케이션 서비스
- `ld.so.preload` 비어 있음 (루트킷 없음)
- **지속성이 전혀 없다는 것이 재부팅만으로 활동이 멈춘 이유다**

### 13. T0 전후 변경 파일

```bash
sudo find / -xdev -newermt "2026-06-28 07:00" ! -newermt "2026-06-28 12:00" \
  -type f 2>/dev/null | grep -vE '^/(proc|sys|run)'
```

- 시스템 영역 변조 없음. 변경 파일은 저널 로그와 npm 로그뿐

## 피해 범위

### 확인된 피해

- 서버 자원 무단 사용 (CPU, 디스크, 네트워크)
- 아웃바운드 데이터 전송 요금 약 2만 원
- 디스크 포화로 인한 서비스 중단 및 예기치 않은 재부팅

### 피해 없음으로 확인

| 항목 | 근거 |
|---|---|
| 채굴 미작동 | `config.json`의 지갑 주소가 기본값 |
| 타 서버 공격 실패 | `exploited.log` 0바이트 |
| 권한 상승 없음 | 악성 파일 전부 `ec2-user` 소유, `ld.so.preload` 비어 있음 |
| SSH 침입 없음 | 로그인 기록 전부 본인, 등록 키 1개 |
| AWS 계정 침해 없음 | CloudTrail 이상 없음, 타 리전 인스턴스 없음 |

### 확인 불가

- 7/4 이후 nginx 로그가 없어 그 이후 웹 접근 여부는 검증할 수 없다
- 디스크 포화 시점 전후로 journald 기록이 유실되었을 가능성이 있다

## 근본 원인

### 직접 원인

**Next.js v15.1.6의 미들웨어 인증 우회 취약점**을 통한 원격 코드 실행.

nginx 로그의 `POST /` 공격이 08:58:19~08:59:14에 집중되고, XMRig 파일의 `Birth`가 08:58:22로 그 구간 안에 위치한다. 서로 독립적인 두 증거의 시각이 일치하므로 이 요청이 침입 경로임이 확정된다.

### 기여 요인

| 요인 | 영향 |
|---|---|
| 프레임워크 버전 미관리 | 알려진 취약점이 패치되지 않은 채 노출 |
| 애플리케이션 디렉터리 권한 777 | RCE 성공 후 파일 기록이 자유로웠음 |
| 모니터링 부재 | 10일간 감염 사실을 인지하지 못함 |
| 로그 로테이션 미적용 | `data.log` 무제한 증가 방치 |

- IMDSv2 강제 설정

- CloudWatch 디스크 사용률 알람 설정
- 예산 알람 유지 (이번 사고의 실제 발견 경로)
- GitHub Dependabot 활성화로 의존성 취약점 자동 감지
- 로그 로테이션 정책 점검

## 배운 점

**탐지가 가장 큰 문제였다.**
침입은 1분 만에 끝났지만 인지까지 10일이 걸렸다. 취약점은 앞으로도 계속 발견될 것이므로 "뚫리지 않는 것"을 목표로 삼기보다, 뚫렸을 때 얼마나 빨리 알아차리는지를 개선하는 편이 현실적이다.

**설정해둔 알람이 실제로 작동했다.**
예산 임계치 알람이 없었다면 발견은 더 늦어졌을 것이다. 사전에 만들어둔 안전장치가 유일한 탐지 수단이었다.

**작은 디스크가 피해를 제한했다.**
8GB라는 제한 때문에 스캐너가 자기 로그로 디스크를 채워 스스로 멈췄다. 100GB였다면 훨씬 오래 활동했을 것이다. 의도한 방어는 아니었지만, 자원 제한이 피해 범위를 제한할 수 있다는 점은 기억할 만하다.

**지속성 여부가 사고 규모를 가른다.**
웜이 cron이나 systemd에 등록만 했더라도 재부팅 후 다시 살아나 훨씬 오래 지속되었을 것이다. 조사에서 지속성 확인이 왜 필수 단계인지 체감했다.

**침해된 서버는 고치지 않고 버리는 것이 정답이다.**
악성 파일만 지우는 것으로는 무엇이 남았는지 확신할 수 없다. 재구축이 더 빠르고 확실하다.

**급할 때는 일단 격리하는 것이 맞았다.**
7/4에 시간이 없어 상세 조사 없이 인스턴스를 중지한 것은 결과적으로 옳은 판단이었다. 원인 파악은 나중에 해도 되지만, 진행 중인 피해를 멈추는 것은 즉시 해야 한다. 다만 그 시점에 스냅샷을 떴다면 더 좋았을 것이다.
