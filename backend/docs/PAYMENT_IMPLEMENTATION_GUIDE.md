# 결제 시스템 구현 가이드

## 현재 구현 상태 (테스트 모드)

### 현재 흐름
1. 주문 생성 → `PENDING_PAYMENT` 상태
2. **자동으로 결제 승인 API 호출** (프론트엔드에서)
3. 결제 승인 → `PAID` → `ACTIVE` 상태

### 특징
- 실제 PG사 연동 없음
- 고객의 계좌/카드 정보 확인 없음
- 항상 결제 승인 성공으로 처리
- 테스트/개발 환경용

## 실제 이커머스 결제 시스템 구조

### 1. 결제 참여 주체

```
고객 (카드/계좌)
    ↓
우리 서버 (주문 생성)
    ↓
PG사 (Payment Gateway) - 토스페이먼츠, 이니시스, KG이니시스 등
    ↓
카드사/은행 (실제 결제 처리)
    ↓
결제 승인/실패 응답
    ↓
우리 서버 (주문 상태 업데이트)
```

### 2. 실제 결제 흐름

#### 단계 1: 주문 생성
- 고객이 주문 정보 입력
- 서버에서 주문 생성 (`PENDING_PAYMENT`)
- **아직 결제는 이루어지지 않음**

#### 단계 2: 결제 요청 (프론트엔드)
- PG사 결제 위젯/API 호출
- 고객이 카드 정보 입력 (PG사 페이지에서)
- **우리 서버는 카드 정보를 받지 않음** (보안상 PG사가 직접 처리)

#### 단계 3: PG사 처리
- PG사가 카드사/은행에 결제 요청
- 카드사/은행이 고객 계좌/카드 잔액 확인
- 승인/거절 결정

#### 단계 4: 결제 결과 통보 (Webhook/Callback)
- PG사가 우리 서버에 결제 결과 통보
- 우리 서버에서 주문 상태 업데이트
  - 승인 성공: `PENDING_PAYMENT` → `PAID` → `ACTIVE`
  - 승인 실패: `PENDING_PAYMENT` → `PAYMENT_FAILED`

## 결제 구현 범위

### 현재 구현 (테스트 모드) ✅
- [x] 주문 생성 시 결제 대기 상태 설정
- [x] 결제 승인 API (테스트용)
- [x] 결제 실패 API (테스트용)
- [x] 주문 상태 전이 로직

### 실제 운영을 위해 추가 필요

#### 1. PG사 연동 (필수)
- 토스페이먼츠, 이니시스, KG이니시스 등 선택
- PG사 SDK/API 연동
- 결제 위젯 프론트엔드 통합

#### 2. 결제 요청 처리
- PG사 결제 요청 API 호출
- 결제 키/ID 발급
- 결제 페이지 리다이렉트

#### 3. 결제 결과 처리 (Webhook/Callback)
- PG사에서 결제 결과 통보 받기
- 결제 승인/실패에 따른 주문 상태 업데이트
- 중복 처리 방지 (Idempotency)

#### 4. 보안
- 결제 정보 암호화
- 결제 금액 검증 (변조 방지)
- 결제 키 검증

### 구현하지 않는 것 (PG사가 처리)
- ❌ 고객의 계좌 잔액 확인 (카드사/은행이 처리)
- ❌ 카드 정보 저장 (PG사가 처리, PCI-DSS 준수)
- ❌ 실제 돈 이체 (카드사/은행이 처리)

## 결제 구현 단계별 추천

### Phase 1: 현재 (테스트 모드) ✅
- 주문 생성 → 자동 결제 승인
- 개발/테스트용

### Phase 2: PG사 연동 준비
- PG사 계약 및 테스트 환경 설정
- 결제 요청/결과 처리 구조 설계

### Phase 3: PG사 연동 구현
- PG사 SDK 통합
- 결제 위젯 프론트엔드 통합
- Webhook/Callback 처리

### Phase 4: 운영 환경
- 실제 결제 처리
- 결제 실패 처리
- 환불 처리

## 현재 구현의 장점

1. **개발 속도**: 실제 PG 연동 없이도 전체 흐름 테스트 가능
2. **비용 절감**: PG사 테스트 환경 비용 없음
3. **유연성**: 나중에 PG사 교체 시 서비스 로직만 수정

## 결론

**현재는 테스트 모드로 구현되어 있습니다.**
- 주문 생성 시 자동으로 결제 승인 처리
- 실제 PG 연동은 나중에 추가하면 됩니다
- 고객의 계좌/카드 정보는 PG사가 처리하므로 우리가 직접 확인할 필요 없습니다
